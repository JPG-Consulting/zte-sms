# ZTE MF833U1 — Observed HTTP API

**Evidence level:** Locally verified through Chrome Developer Tools, Postman, and selected Home Assistant integration tests on one ZTE MF833U1.

This document describes observed behavior, not an official ZTE API specification. Other models and firmware versions may behave differently.

## 1. Base URL

```text
http://192.168.0.1
```

The modem's SMS interface is available at:

```text
http://192.168.0.1/index.html#sms
```

All experiments were performed without changing the modem's firmware, USB mode, APN, or MikroTik LTE failover configuration.

## 2. Read stored SMS — verified

### Endpoint

```http
GET /goform/goform_get_cmd_process?isTest=false&cmd=sms_data_total&page=0&data_per_page=500&mem_store=1&tags=10&order_by=order+by+id+desc HTTP/1.1
Host: 192.168.0.1
Referer: http://192.168.0.1/index.html
```

### Important headers

In Postman, the `Referer` header was necessary for the successful test.

With:

```http
Referer: http://192.168.0.1/index.html
```

The modem returned a JSON object containing a `messages` array.

Without this header, the observed response was:

```json
{"sms_data_total":""}
```

The `X-Requested-With` header was not necessary in the browser test.

A timestamp-like `_` query parameter appeared in some browser requests but was not necessary for the successful Postman test.

These observations do not prove that other firmware versions have identical requirements.

### Sanitized response example

```json
{
  "messages": [
    {
      "id": "3",
      "number": "+34000000000",
      "content": "005000720075006500620061",
      "tag": "1",
      "date": "26,10,24,15,06,16,+8",
      "draft_group_id": "",
      "received_all_concat_sms": "1",
      "concat_sms_total": "0",
      "concat_sms_received": "0",
      "sms_class": "4"
    }
  ]
}
```

The phone number is a placeholder. The content example decodes to `Prueba`.

The ZTE web interface interprets `tag` values as described in section 8.11. The exact meanings of `mem_store` and `tags` have not been independently established.

### Stored-message `date` — observed on MF833U1

The returned `date` uses comma-separated components resembling `YY,MM,DD,HH,mm,ss,timezone_offset`. During read-only comparisons of outgoing records with the recipient iPhone's **individual message timestamps**, these examples were observed:

| Modem `date` | iPhone display | Interpretation of suffix |
|---|---|---|
| `26,10,24,19,13,23,+8` | 24 Oct, 19:13 | `+8` quarter-hours = UTC+2 |
| `26,10,24,19,39,44,+8` | 24 Oct, 19:39 | `+8` quarter-hours = UTC+2 |
| `26,10,25,16,32,21,+4` | 25 Oct, 16:32 | `+4` quarter-hours = UTC+1 |
| `26,10,25,16,34,02,+4` | 25 Oct, 16:34 | `+4` quarter-hours = UTC+1 |

The suffix values and their change across the October 2026 daylight-saving transition are **consistent with timezone offsets expressed in 15-minute units**. The recorded times matched the recipient's individual message times to the displayed minute in these examples. This is observed behavior on the tested MF833U1, **not** a confirmed firmware specification or proof of the timestamp's origin. An iPhone conversation's group header shows the first message's time and must not be interpreted as the timestamp of every message in the group.

The `date` field can provide supporting evidence when inspecting stored SMS, but does **not** prove delivery, identify which client originated a message, or by itself authorize deletion. The source of the timestamp (SMSC, modem, or another conversion) remains unverified.

## 3. SMS content encoding — verified

The `content` field returned by the modem contains hexadecimal UTF-16 big-endian data.

Example:

```text
005000720075006500620061
```

Decodes to:

```text
Prueba
```

Python example:

```python
def decode_sms_hex(value: str) -> str:
    return bytes.fromhex(value).decode("utf-16-be")
```

The implementation should handle malformed hexadecimal data and UTF-16 surrogate pairs.

## 4. Send SMS — verified

The SMS sending endpoint was captured directly from the MF833U1 web interface and reproduced successfully in Postman.

SMS sending has also been verified through the Home Assistant integration using `zte_sms.send_sms` and the `notify.zte_sms` notification entity.

### Endpoint

```http
POST /goform/goform_set_cmd_process HTTP/1.1
Host: 192.168.0.1
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
Referer: http://192.168.0.1/index.html
```

The original browser request also contained:

```http
Origin: http://192.168.0.1
X-Requested-With: XMLHttpRequest
```

These headers were observed, but their necessity for sending has not been independently established.

### Form parameters

The request body uses `application/x-www-form-urlencoded`.

| Parameter | Observed value or purpose |
|---|---|
| `isTest` | `false` |
| `goformId` | `SEND_SMS` |
| `notCallback` | `true` |
| `Number` | Destination phone number |
| `sms_time` | Timestamp |
| `MessageBody` | SMS text encoded as hexadecimal UTF-16BE |
| `ID` | `-1` |
| `encode_type` | SMS encoding mode |

### Sanitized example

```text
isTest=false
goformId=SEND_SMS
notCallback=true
Number=+34000000000
sms_time={{sms_time}}
MessageBody=005000720075006500620061
ID=-1
encode_type=GSM7_default
```

When sending this as `x-www-form-urlencoded`, the HTTP client must correctly encode special characters such as `+` and `;`.

The phone number above is fictional.

The example preserves the original observed GSM7 encoding mode. The current Home Assistant integration uses `encode_type=UNICODE`.

### Successful response

Postman returned:

```json
{"result":"success"}
```

The SMS was also confirmed as received on the destination phone.

The ZTE web UI subsequently checks `sms_cmd_status_info` with `sms_cmd=4` before reporting its own send success (section 8.12). The initial API response alone is **not** a verified final modem-operation outcome or a network delivery receipt. Delivery was verified separately during the experiments.

## 5. SMS timestamp — partially verified

The captured browser request contained a timestamp resembling:

```text
26;10;24;16;03;44;+2
```

Its apparent structure is:

```text
YY;MM;DD;HH;mm;ss;timezone_offset
```

A Postman pre-request script was used to generate a current timestamp in the `Europe/Madrid` timezone.

### Postman pre-request script

```javascript
const now = new Date();

const parts = new Intl.DateTimeFormat("en-GB", {
  timeZone: "Europe/Madrid",
  year: "2-digit",
  month: "2-digit",
  day: "2-digit",
  hour: "2-digit",
  minute: "2-digit",
  second: "2-digit",
  hourCycle: "h23"
}).formatToParts(now);

const get = (type) =>
  parts.find(p => p.type === type).value;

const offset = new Intl.DateTimeFormat("en-US", {
  timeZone: "Europe/Madrid",
  timeZoneName: "longOffset"
}).formatToParts(now)
  .find(p => p.type === "timeZoneName").value;

const hours = Number(
  offset.match(/GMT([+-]\d+)/)?.[1] ?? 0
);

const smsTime = [
  get("year"),
  get("month"),
  get("day"),
  get("hour"),
  get("minute"),
  get("second"),
  hours >= 0 ? `+${hours}` : `${hours}`
].join(";");

pm.variables.set("sms_time", smsTime);

console.log("sms_time:", smsTime);
```

In Postman's form body:

```text
sms_time = {{sms_time}}
```

### ZTE web UI timestamp implementation — source inspected

The device-served `js/util.js` defines `getCurrentTimeString(date)`, called by `js/service.js` when constructing `SEND_SMS`. It takes a JavaScript `Date` (or `new Date()`), formats the **browser's local** year, month, day, hour, minute, and second, and appends `-getTimezoneOffset() / 60`, with a leading `+` for positive offsets. Therefore the outgoing `sms_time` suffix is expressed in **hours**, for example `+2` during Madrid summer time and `+1` during winter time. This agrees with the existing Python `sms_timestamp()` field format.

**Do not confuse the formats:** outgoing `sms_time` is semicolon-separated and uses an offset in **hours**; stored `date` is comma-separated and its observed suffix is consistent with **quarter-hours**. We have not established whether or how the firmware derives stored `date` from outgoing `sms_time`.

**Important:** Successful sending experiments and source inspection support the format above, but firmware-specific timestamp handling and the origin of stored-message timestamps still need investigation.

The current integration uses the `Europe/Madrid` timezone for SMS timestamps. This is a known limitation and should not be assumed correct for all installations. **Pending FIX before future send-verification work:** evaluate using Home Assistant's configured timezone (`hass.config.time_zone`) instead, and validate the expected modem behavior before implementing the change.

## 6. Unicode and accented characters — verified

A second experiment investigated accented characters.

### Test message

```text
Prueba áéíóú ñ
```

### UTF-16BE hexadecimal representation

```text
005000720075006500620061002000E100E900ED00F300FA002000F1
```

### Test A: GSM7_default

Parameter:

```text
encode_type=GSM7_default
```

Received SMS:

```text
Prueba @é@@@ ñ
```

**Result: Incorrect.**

Several accented characters were replaced with `@`.

### Test B: UNICODE

Only the encoding parameter was changed:

```text
encode_type=UNICODE
```

Postman returned:

```json
{"result":"success"}
```

Received SMS:

```text
Prueba áéíóú ñ
```

**Result: Correct.**

### Conclusion

On the tested MF833U1, `encode_type=UNICODE` successfully preserved all the tested accented characters.

The Home Assistant integration uses this mode, and real SMS reception has been verified.

Although the browser's original request used `GSM7_default` for plain text, its `MessageBody` was still represented as hexadecimal UTF-16BE.

The exact internal handling of encoding modes remains unverified.

### Implementation considerations

- Use UTF-16BE hexadecimal representation for `MessageBody`.
- Use `UNICODE` for reliable handling of the tested accented characters.
- Do not assume that emojis or long messages work without further tests.
- Account for SMS length differences between GSM 7-bit and Unicode SMS.

### 8.9 Polling versus page initialization — partially observed

During inspection of the Device SMS page, some GET requests were observed to repeat without the operator clicking anything. This is evidence that the web interface performs some automatic polling while the page is open.

The general status polling loop is confirmed by `js/service.js`: after each status response or error it schedules another iteration with `setTimeout(..., 1000)`. Thus the delay is one second after completion, not necessarily a fixed one-second request-to-request interval. The exact repetition schedule of the other commands has not been established. The observed order during page initialization included:

1. `sms_cmd_status_info`
2. `pbm_init_flag`
3. `sms_data_total`
4. `sms_capacity_info`
5. `pbm_data_total`

Other requests observed around the same time included the general modem status query, wireless configuration query, `sms_unread_num`, and `upgrade_result`. The general status loop is confirmed in source; membership of the other commands in a periodic polling cycle has not been confirmed individually. `js/sms/smslist.js` additionally registers a one-second interval that checks the cached status field `sms_db_change` and refreshes SMS capacity and send-button state when its value is `"1"`. This does not, by itself, prove that the inbox list is reloaded or that the flag reliably detects every change.

Do not reproduce the web interface's polling in the integration without a separate requirement and further investigation. In particular, do not add these requests before or after `SEND_SMS`; keeping the send path fast remains a project requirement.

### 8.11 Stored message tags — ZTE web UI interpretation

Inspection of the device-served `js/service.js` and `js/sms/smslist.js` clarifies how the web UI handles message tags:

| `tag` | Interpretation in the web UI | Supporting behavior |
|---|---|---|
| `"0"` | Received, read | Rendered using the incoming-message template |
| `"1"` | Received, unread/new | `service.js` maps this to `isNew=true`; rendered as incoming |
| `"2"` | Sent | Rendered using the outgoing-message template |
| `"3"` | Failed outgoing message | Rendered using the outgoing-message template; UI also assigns this tag on send failure |
| `"4"` | Draft | Displayed as a draft or populated into the compose field |

These are **web UI classifications**, not proof of carrier delivery or a complete firmware specification. The four observed records (`tag="2"` three times, `tag="1"` once) agree with the observed storage and unread counters. A tag does **not** establish whether a message originated from Home Assistant, Postman, the modem UI, or another client.

The UI's `setAsRead` operation sends `goformId=SET_MSG_READ`, `msg_id` as semicolon-delimited IDs, and `tag=0` when a conversation with new messages is opened. This is a state-changing operation and is **not** required for read-only inspection; do not call it automatically from this integration.

### 8.12 Send operation status — ZTE web UI workflow

The modem-served `js/service.js` implements the following send workflow:

1. POST `goformId=SEND_SMS` with a single `Number`, encoded `MessageBody`, `ID`, `sms_time`, and `encode_type`.
2. If the initial response does not contain `result="success"`, invoke the UI's failure callback.
3. If the initial response is `result="success"`, wait **1 second** and GET `sms_cmd_status_info` with `sms_cmd=4`.
4. Interpret `sms_cmd_status_result="3"` as success and `"2"` as failure. For other values, schedule another status query after 1 second.
5. If a status request fails or yields no usable response, invoke the failure callback.

The status checker does not show a finite retry limit in the inspected function. These details establish how the **web UI** classifies its send operation; they do not prove final delivery to the recipient. A transport timeout or a failed status query can leave the actual send outcome **uncertain**, even if the UI reports failure. Do not automatically retry an uncertain send: doing so may create duplicates.

The same service code uses `sms_cmd=5` for draft-save status and `sms_cmd=6` for deletion status. The readiness check uses `sms_cmd=1`. No conclusion about unrelated command codes should be inferred from these mappings.

**Integration design decision:** preserve the current fast send path without pre-send polling, forced post-send polling, or automatic retries. Treat `result="success"` as an initial API acceptance indication, not a verified final delivery receipt. Review error classification separately in B-02 before changing behavior. A controlled, explicitly authorized single-SMS experiment could compare the initial response, `sms_cmd=4`, and the resulting stored record.

### 8.13 Message storage, IDs, and deletion safety

After a send callback, `js/sms/smslist.js` calls `getLatestMessage()`, which requests up to five recent stored messages (`mem_store=1`, `tags=10`, descending ID) and selects the first with `tag="2"` or `tag="3"`. This is a **UI heuristic**, not a transaction-specific mapping between `SEND_SMS` and a stored message ID. A concurrent or unrelated send could make the most recent matching record belong to a different operation.

The UI also reads `sms_capacity_info` to display used/total device storage and disables sending when its cached `nvUsed` is at least `nvTotal`. For multiple selected recipients it checks whether the recipient count plus used slots exceeds the total. This reflects UI behavior, not proof of exact modem allocation for every message or multipart SMS.

#### Message IDs after deletion — observed on MF833U1

In a user-observed test, the modem's web UI displayed one conversation while its storage indicator showed `15/100`. After the user deleted that conversation from the conversation list, the indicator changed to `0/100` and a subsequent `sms_data_total` query returned no messages. This is consistent with the visible conversation representing multiple stored records, but **the precise deletion command and number of IDs deleted were not captured**. One visible conversation must not be assumed to represent one stored SMS.

Previously inspected stored records included ID `17`. After clearing the stored messages, the user sent three more SMS, deleting the first two; the third was retained and observed as the only stored message, with ID `20`. This demonstrates that **deleting messages did not reset the observed ID sequence to 1**. IDs `18` and `19` are consistent with the two intervening sends but were **not independently captured**, so their exact assignment remains unverified.

The stored-message `id` must not be treated as a storage-occupancy counter or assumed to be contiguous among currently stored messages. The maximum ID value, wraparound behavior, and possible ID reuse remain unknown. Do not infer that IDs are limited to the reported `100` storage slots, or use the ID sequence alone to identify or delete integration-originated messages.

The service exposes state-changing commands such as `DELETE_SMS` and `SET_MSG_READ`. The SMS list UI also offers bulk deletion and, in its resend flow, deletion of the prior record after a subsequent send callback. **None of these actions should be copied into automatic integration cleanup.** Never delete a received, manually created, or ambiguously attributed message. Do not use `tag`, recency, phone number, or storage counters alone as proof of integration provenance.

### 8.14 Five recipients, multipart messages, and batching

The web UI's contact picker sets `max_selected_options: 5`, but its send handler iterates through selected numbers and calls `sendSMS` **once per recipient**, sequentially. Its `SEND_SMS` request uses a single `Number` field. This is not evidence that the API supports sending to five recipients in one request.

Separately, the composer displays `getSmsCount(text)/5` and uses a maximum of five SMS segments in its UI counter. This is a message-length/segment UI constraint, **not** a five-recipient batch API.

The `SAVE_SMS` **draft** request does use `SMSNumber` formed from numbers joined with semicolons and a trailing semicolon. This proves semicolon-delimited recipients are used for drafts, **not** that `SEND_SMS.Number` accepts that format. Multi-recipient `SEND_SMS` support remains unverified; do not test arbitrary delimiter formats or send parallel SMS without an explicitly authorized, controlled experiment.

### 8.15 Source and evidence limitations

The findings in sections 8.11–8.14 come from minified JavaScript served by the tested modem (`js/service.js` and `js/sms/smslist.js`), interpreted alongside the earlier HTTP captures. They describe client-side behavior and API calls, not an official modem protocol contract. Some failure callbacks may collapse distinct underlying outcomes into a generic error. They do not establish an authenticated transaction ID, a delivery receipt, or safe automatic deletion criteria.

### 8.16 SMS delivery-report settings and report query — partially verified

The modem's **SMS Settings** page exposes a **Delivery Report** setting with **Enable** and **Disable** options. During a read-only inspection, **Disable** was selected. A GET request to `goform_get_cmd_process` with `isTest=false&cmd=sms_parameter_info` returned `sms_para_status_report="0"`. Together, these observations confirm that `"0"` corresponds to the disabled setting on this device. The value for **Enable** is expected to be `"1"`, but was not independently observed. The setting was not changed, and **Apply** was not pressed.

Inspection of the modem-served `js/service.js` also identified:

- `sms_parameter_info`: the web UI reads `sms_para_status_report` and exposes it as `deliveryReport`.
- `SET_MESSAGE_CENTER`: the web UI passes the delivery-report selection as `status_save` when saving SMS settings. This is a state-changing operation and was **not** invoked.
- `sms_status_rpt_data`: a GET query with `page` and `data_per_page` parameters; the web UI code expects a `messages` array.
- `sts_received_flag`: a field that the web UI uses as an apparent status-report notification indicator. Its firmware semantics and any side effects of associated status queries remain unverified.

A controlled, read-only request was made using:

```http
GET /goform/goform_get_cmd_process?isTest=false&cmd=sms_status_rpt_data&page=0&data_per_page=5 HTTP/1.1
Host: 192.168.0.1
Referer: http://192.168.0.1/index.html
X-Requested-With: XMLHttpRequest
```

Observed response:

```json
{"messages":[]}
```

The empty array **does not prove** that the endpoint is unsupported or that no delivery reports could exist: delivery reports were disabled at the time, and the exact firmware behavior and pagination semantics have not been verified. Earlier tests also established that an incorrect or missing `Referer` can produce misleading empty API responses; the controlled request above retained the working web-interface referrer.

In a separate, explicitly authorized test, **one SMS** was sent through the modem's web interface. The `SEND_SMS` POST returned `{"result":"success"}`, and the subsequent GET `sms_cmd_status_info` with `sms_cmd=4` returned `{"sms_cmd":"4","sms_cmd_status_result":"3"}`. The recipient independently confirmed receipt on the handset. These modem responses indicate success according to the web UI's send workflow, **not** independently verified carrier acceptance or handset delivery receipts. No additional SMS was sent during the delivery-report investigation.

**Integration decision:** Do not change the delivery-report setting, add mandatory post-send polling, or introduce automatic retries. Delivery-report support remains a research topic, not a dependency of the fast outbound SMS path.

## 9. Current integration status

The Home Assistant integration currently provides:

- Configuration of the modem host.
- Configuration and editing of default SMS recipients.
- `zte_sms.send_sms` for sending to one explicitly specified number.
- `notify.zte_sms` for sending individually to configured default recipients.
- UTF-16BE hexadecimal encoding with `encode_type=UNICODE`.
- On-demand SMS reading functionality in the HTTP client.

The integration does not currently provide incoming SMS entities, automation triggers, periodic inbox polling, SMS storage monitoring, or automatic deletion.

For implementation architecture, see [Architecture](../architecture.md).

## 11. Safety and privacy

The modem HTTP API should only be accessed from a trusted local network.

Do not expose the modem management interface to the public internet.

Never commit or publish:

- Real telephone numbers.
- Private SMS content.
- Cookies or session tokens.
- Credentials.
- Unredacted HTTP captures.

Use fictional data in documentation and automated tests.

Do not perform live SMS sending, marking messages as read, or deletion in automated tests without explicit authorization.

Never automatically delete received SMS, manually sent SMS, or messages whose origin cannot be unambiguously established.

Do not change the modem's firmware, USB mode, APN, or MikroTik network configuration as part of this integration.
