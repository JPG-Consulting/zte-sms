# Architecture

## Overview

ZTE SMS is a Home Assistant custom integration that communicates with compatible ZTE LTE modems through their local HTTP API.

The initial supported development target is the **ZTE MF833U1**.

The current implementation focuses on **outbound SMS**. It provides a Home Assistant action and notification entity for sending messages.

The first stable-release milestone prioritizes fast, reliable SMS submission and safe cleanup of messages generated by the integration. Automatic cleanup is not yet implemented.

Incoming-message automation, local archiving, message synchronization, and periodic cellular monitoring are later milestones.

```text
Home Assistant
    |
    +-- ZTE SMS config entry
    |       |
    |       +-- Modem host
    |       +-- Default SMS recipients
    |
    +-- zte_sms.send_sms action
    |       |
    |       +-- One explicit recipient
    |
    +-- notify.zte_sms entity
            |
            +-- Configured default recipients
                    |
                    v
               ZTEClient
                    |
                    v
          Local ZTE HTTP API
                    |
                    v
               ZTE MF833U1
                    |
                    v
              Mobile network
```

The integration does not manage the MikroTik router or its LTE failover configuration.

## Implemented components

### Configuration and options

`custom_components/zte_sms/config_flow.py`

The configuration flow collects the modem host and an optional list of default SMS recipients.

The options flow allows the recipient list to be updated.

Phone numbers are validated in international format, starting with `+` followed by digits. Duplicate recipients are removed.

The default modem host is `192.168.0.1`.

### HTTP client

`custom_components/zte_sms/client.py`

The client encapsulates communication with the modem's local HTTP API.

Outbound messages use the MF833U1 `SEND_SMS` operation.

SMS text is encoded as UTF-16BE hexadecimal data and sent using `encode_type=UNICODE`.

This encoding has been verified with Spanish accented characters and `ñ` on the tested device.

The client also contains on-demand message-reading functionality. This does not imply that Home Assistant currently exposes incoming SMS entities or periodically retrieves messages.

For verified HTTP request details, see [MF833U1 HTTP API](api/mf833u1.md).

### Integration setup and SMS action

`custom_components/zte_sms/__init__.py`

The integration creates a modem client for the configured Home Assistant entry and registers the `zte_sms.send_sms` action.

The action requires:

- `number`: one explicit destination phone number.
- `message`: the SMS text.

The action sends a request when invoked. It does not schedule periodic sending.

### Notification entity

`custom_components/zte_sms/notify.py`

The integration provides a modern Home Assistant notification entity, `notify.zte_sms`.

When `notify.send_message` is invoked for this entity, the integration retrieves the configured default recipients and submits an individual SMS request for each recipient.

The entity requires at least one configured default recipient.

A successful API response indicates that the modem accepted the request. It does not independently establish delivery to the destination phone.

## Runtime behavior

### Outbound SMS — critical path

Outbound SMS submission is the integration's primary responsibility.

The intended runtime sequence is:

1. A Home Assistant user or automation invokes the SMS action or notification entity.
2. The integration identifies the destination recipient or configured recipient list.
3. The HTTP client encodes the message and submits it to the modem.
4. The modem returns an API response or the request encounters an error.
5. The integration reports the known result to the caller.

The submission path must remain independent of nonessential operations.

**Critical-path rule:** an outbound SMS must not wait for inbox synchronization, cellular status checks, local archive writes, or stored-message cleanup.

This requirement is particularly important for time-sensitive alarm notifications.

The integration must not perform preliminary modem queries solely to confirm signal availability before attempting submission.

Comprehensive failure classification, uncertain-outcome handling, and diagnostic logging remain areas for improvement.

Automatic retries must not be introduced where they could result in duplicate SMS submissions.

A modem response indicating successful submission is not independent proof of delivery to the recipient.

### Post-submission sent-message cleanup — Milestone 1

Safe cleanup of messages generated by the integration is part of the first stable-release milestone.

The modem may store outbound SMS records. Whether integration-generated messages occupy that storage, and how they can be identified, must be verified experimentally.

If a safe cleanup mechanism is established, the intended behavior is:

1. Submit the SMS without waiting for storage-management operations.
2. Establish the submission outcome as reliably as the modem API permits.
3. Identify the exact stored message using verified integration ownership and a reliable modem message identifier.
4. Respect the user's option to retain integration-generated messages in modem storage.
5. Delete only an eligible, positively identified integration-generated record.
6. Handle cleanup errors separately from submission errors, without automatically resending the SMS.

Cleanup must not delay initial SMS submission. Its scheduling and concurrency behavior must be designed and tested before implementation.

The user must be able to opt out of automatic cleanup if the feature is supported.

**Safety gate:** automatic deletion is prohibited unless the integration can reliably prove ownership of the exact stored message and verify that deletion does not interfere with transmission.

Matching recipient, content, timestamp, or sent-folder location alone is insufficient.

Received messages and messages sent manually through the modem interface must never be deleted by integration cleanup.

If safe deletion cannot be established, the integration must not implement speculative cleanup or claim to prevent storage exhaustion. The limitation must be investigated and resolved appropriately before the milestone can be considered complete.

### Incoming SMS

The HTTP API and decoding format have been investigated, and the client contains on-demand message-reading functionality.

However, the integration currently has no incoming SMS entity, event, automation trigger, or scheduled inbox retrieval.

Incoming-message synchronization and automation are not part of Milestone 1.

### Background activity

The current integration does not schedule periodic SMS inbox polling or cellular-signal monitoring.

It does not automatically delete, mark as read, or otherwise modify stored messages.

No periodic polling is required for the current outbound SMS functionality.

## Safety boundaries

### LTE fallback

The modem also provides an LTE Internet connection used for fallback through a MikroTik router.

The integration must not modify:

- MikroTik routing or failover rules.
- Modem firmware or USB mode.
- APN or cellular network configuration.
- Existing Internet connectivity settings.

SMS functionality must remain independent of router management.

### SMS storage and deletion

The modem maintains its own SMS storage.

The current integration does not automatically delete messages.

Before adding deletion, development must establish reliable message provenance, exact identifiers, and safe deletion semantics through authorized testing.

The integration must never use broad folder cleanup, guessed message IDs, or content matching as substitutes for verified ownership.

Storage exhaustion and cleanup failure must be handled and documented explicitly.

### Privacy

SMS contents, phone numbers, credentials, cookies, and session tokens are sensitive.

They must not be exposed through diagnostic logs or committed test fixtures.

Automated tests must use synthetic data and must not contact a live modem.

Future local message archiving must require explicit user consent, with appropriate retention, access-control, and backup considerations.

## Future architecture — after Milestone 1

The following capabilities are possible later extensions. They are not required for the first stable release and must not delay its completion.

### Optional local SMS archive and viewer

A future implementation may allow users to retain copies of messages sent by this integration in Home Assistant storage rather than relying exclusively on modem storage.

The initial scope would be integration-generated outbound SMS. Archiving received messages would be considered separately.

Possible requirements include:

- Optional local persistence, with a suitable Home Assistant-compatible storage mechanism.
- Explicit consent for storing message contents.
- Privacy, retention, access-control, and backup policies.
- Recorded submission outcomes, including uncertain results.
- A Home Assistant user interface for viewing locally archived messages.
- Clear separation between local archive records and modem-stored records.
- No blocking archive writes in the critical SMS submission path.

**Local archiving must not be considered a complete user-facing feature without a usable message viewer.**

An internal archive identifier must not be treated as proof of ownership of a stored modem message.

### On-demand modem queries

A future read-only query may retrieve current modem information or stored messages when explicitly requested.

Examples include:

- A manual LTE status check.
- A signal or network-registration query.
- Reading messages currently stored in the modem.
- A manual **Sync now** operation in a future message viewer.

An on-demand query performs a bounded operation. It does not start continuous monitoring or automatically detect subsequent changes.

The future viewer may support both locally archived messages and messages retrieved directly from modem storage, with each source clearly identified.

### Optional incoming SMS synchronization

Automatic detection of newly received messages would require repeated checks or another notification mechanism verified on the modem.

A future implementation may provide:

- Manual synchronization without periodic polling.
- Optional polling, disabled by default.
- Stable message identification and restart-safe deduplication.
- Safe pagination and multipart-message handling.
- Explicit privacy and retention behavior.
- Optional incoming-message events or automation triggers.

Reading messages must not inadvertently mark them as read or delete them.

Any synchronization must remain independent of outbound SMS submission and must not monopolize modem access in a way that delays urgent alerts.

### Optional cellular monitoring

A future monitoring component may expose modem reachability, network registration, and signal information.

On-demand status queries and periodic monitoring are separate capabilities.

Periodic monitoring must be opt-in, use a configurable refresh interval, and remain independent of the MikroTik router.

Future automations, such as Alarmo, may request temporary monitoring. The design must avoid one automation disabling monitoring still needed by another or explicitly enabled by the user.

Signal loss must not automatically be interpreted as deliberate interference or jamming.

### Modem access and concurrency

Future synchronization, monitoring, and archiving must not compromise the priority of outbound SMS.

Before introducing concurrent modem operations, investigate:

- Whether the modem safely handles overlapping HTTP requests.
- Whether long-running queries delay SMS submission.
- Appropriate request timeouts and cancellation behavior.
- How maintenance operations should yield to urgent sending requests.

No absolute latency or delivery guarantee is implied. Cellular availability and modem behavior remain external constraints.
